# Pretraining a GPT from scratch on many GPUs, and fitting its scaling law

**Status: code complete and tested on CPU, including 2-process DDP and FSDP. The GPU runs have not been made yet,** so there are no measured numbers below. Every number this README will show comes from files in `results/`.

The project has three parts:
1. **A pretraining stack:** a GPT on FineWeb-Edu that runs on one GPU, with DDP, or with FSDP2 (`torchrun`). It reports throughput and **MFU** (model FLOPs utilisation) every step.
2. **A scaling law:** a Chinchilla-style **IsoFLOP sweep** of 13 runs over 3 compute budgets, fitted two independent ways to estimate how the compute-optimal model size grows with compute.
3. **A parallelism benchmark:** DDP vs. FSDP throughput and memory on the same node.

## Model and data
| | |
|---|---|
| Model ([`gpt.py`](gpt.py)) | decoder-only Transformer: pre-norm RMSNorm, rotary position embeddings, GELU MLP, tied embeddings, PyTorch fused attention (Flash kernels) |
| Sizes | 3M · 11M · 25M · 49M · 85M · 201M · 302M non-embedding parameters (d_model ≈ 64 × layers, 64-dim heads) |
| Data ([`prepare_data.py`](prepare_data.py)) | FineWeb-Edu `sample-10BT`, GPT-2 BPE, written as memory-mapped uint16 shards (2B training tokens, 10M validation) |
| Training ([`train.py`](train.py)) | AdamW (β₂ 0.95, weight decay 0.1 on matrices only), warm-up and cosine decay over each run's own budget, bf16, global batch 262k tokens, gradient accumulation, optional `torch.compile` |

## How compute is counted
```
N           = 12 · layers · d²                         non-embedding parameters (attention 4d² + MLP 8d²)
FLOPs/token = 6 · (N + V·d)  +  12 · layers · d · T     every matmul fwd+bwd incl. the LM head, plus attention
MFU         = FLOPs/token × tokens/s ÷ (GPUs × peak bf16 FLOP/s)
```
The vocabulary is 50k tokens, so at the small end the LM head costs more than the Transformer blocks. That is why it is counted.

## The scaling-law experiment
For each budget C ∈ {3e16, 1e17, 3e17} FLOPs, every model size whose token count falls between 1 and 300 tokens per parameter is trained for exactly C FLOPs. Validation loss against log(size) is a parabola, and its minimum is that budget's compute-optimal size N_opt.

| Estimate | Method |
|---|---|
| **Approach 2** | parabola minimum per budget, then the slope of log N_opt vs. log C. Sensitivity: refit with each run left out. |
| **Approach 3** | fit L(N, D) = E + A/N^α + B/D^β to all runs (Huber loss on log L, multi-start L-BFGS, as in Chinchilla); exponent = β/(α+β) |
| **Parameter counting** | approach 2 is also refit with total parameters, because the non-embedding vs. total choice moves the exponent at small scale (Pearce & Song, 2024) |

References: Chinchilla found ≈ 0.50 and Kaplan et al. ≈ 0.73. At this study's much smaller scale (3M–85M vs. Chinchilla's 70M–16B), the expected outcome is a noisier estimate. Showing how sensitive it is matters more than the point value.

## Correctness checks (`pytest tests/test_pretraining.py`, 19 tests, ~35 s on CPU)
- **DDP and FSDP produce identical training losses** (rtol 1e-5) in a real 2-process `torchrun` run on CPU/gloo. This checks the sharded update, gradient-sync skipping during accumulation, and full-state-dict checkpointing.
- Both fitting methods **recover a known exponent** (0.452) from data generated by a known L(N, D).
- Parameter and FLOP formulas match the model; every preset's name matches its parameter count.
- Causal masking: changing future tokens leaves past logits unchanged. RoPE preserves norms and depends only on relative position.
- Data shards survive the round trip, `x`/`y` are shifted by one token, and ranks draw different data.
- The model and optimizer can overfit a batch; checkpoints reload into a fresh model.

## Run it
**Single GPU (Colab A100), the full scaling study:**
```bash
pip install torch numpy scipy matplotlib datasets tiktoken
python prepare_data.py --train_tokens 2e9       # ~4 GB of shards; CPU-bound, ~30-60 min
python scaling.py plan                          # 13 runs, 1.8e18 FLOPs, ~4.6 h at 35 % MFU
python scaling.py lr-sweep --preset 25M         # check the per-size learning rates first
python scaling.py run --compile                 # resumable
python scaling.py fit                           # results/scaling_summary.md, isoflop.png, frontier.png
```
**Multi-GPU node (e.g. 8× A100/H100 rented for an hour or two):**
```bash
python scaling.py run --nproc 8 --parallel ddp --budgets 3e16 1e17 3e17 1e18
python scaling.py bench --nproc 8 --preset 302M --micro_batch 16    # DDP vs FSDP table
torchrun --nproc_per_node 8 train.py --preset 302M --parallel fsdp --tokens_per_param 20
```

## Known limitations
- The per-size learning rates follow the GPT-3 paper's trend and are **not tuned per size** here. A mistuned LR at one size bends the parabola. `lr-sweep` checks one size, and Porian et al. (2024) show LR and warm-up tuning account for part of the Kaplan–Chinchilla gap.
- One seed per point. At 3e16 FLOPs, run-to-run noise is comparable to the loss differences between neighbouring sizes.
- Data is sampled as random windows with replacement, less than one epoch per run.
